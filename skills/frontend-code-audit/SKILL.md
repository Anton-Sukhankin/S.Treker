# Frontend Code Audit

## Role

Use this skill as the working procedure for auditing or correcting S-Tracker frontend code.

This skill is not a product specification. Product behavior is defined by the current prototype and `docs/components/<component>/`. Project constraints are defined by `AGENTS.md`.

## Runtime Mode

Select one mode before auditing.

| Mode | When to use | Hard rule |
|---|---|---|
| `vanilla-vite` | Default mode for the current S-Tracker prototype. | React, JSX, ReactDOM, Tend UI, Material UI, corporate DS runtime code, and new dependencies are findings unless the user explicitly requested them. |
| `react-design-system` | Use only after the user explicitly requests React/DS audit, authorized migration, or work inside an already migrated React/DS codebase. | Audit React and DS usage; do not treat React itself as a violation. |

If the requested task does not clearly authorize React or DS work, use `vanilla-vite`.

## Source Hierarchy

Apply sources in this order:

1. User request: scope, allowed changes, migration permission, and whether edits are allowed.
2. `AGENTS.md`: project constraints, source of truth, deletion rules, and current technology boundary.
3. Current prototype behavior: visible interface and working user scenarios.
4. Component specs in `docs/components/<component>/`: structure, behavior, states, contracts.
5. `docs/component-code-map.md`: mapping from product component to implementation files.
6. Relevant files in `src`, `index.html`, `package.json`, build config, and tests if present.

If documentation and code disagree, verify visible behavior before deciding. Do not invent future behavior.

## Scope Contract

Before auditing, define:

- runtime mode;
- target component or code area;
- files to inspect;
- user scenario that must keep working;
- audit type: read-only audit, safe refactor, bug fix, implementation review, generated-code QA, or post-migration QA;
- validation to run;
- whether documentation sync is required after code changes.

Do not scan or rewrite the entire project for a local code task unless the user asks for a full code audit.

## Severity Rules

Use severity consistently.

| Severity | Meaning | Required response |
|---|---|---|
| `P0` | Project does not build/open, critical scenario is unusable, destructive data loss, or obvious exploitable frontend security issue. | Fix if scope allows; otherwise stop and report blocker. |
| `P1` | Documented user scenario breaks, code contradicts `docs/components`, state contract is wrong, or migration boundary is violated. | Fix in the touched scope or report with exact file/line and required decision. |
| `P2` | Maintainability, ownership, accessibility, performance, or generated-code issue likely to cause future bugs. | Fix if local and safe; otherwise report as follow-up. |
| `P3` | Local cleanup, naming, small duplication, weak comment, or non-blocking readability issue. | Fix only when already editing the nearby code; otherwise report briefly. |

Do not inflate severity because code style differs from preference. Severity must be tied to user-visible behavior, project boundary, safety, or maintainability risk.

## Correction Rules

Apply code changes only when all conditions are true:

- the user allowed edits or the task asks for correction;
- the affected scope is clear;
- current behavior can be preserved or the requested behavior is explicit;
- the change does not introduce new dependencies, runtime stack, or future functionality;
- validation can be run or the skipped validation can be explained.

Report without editing when:

- the fix requires product choice;
- the fix requires React/DS migration not explicitly requested;
- the fix requires new dependencies or package installation;
- the fix requires backend/API design;
- the code behavior conflicts with documentation and the prototype cannot be verified.

## Audit Criteria Matrix

Use this matrix for both runtime modes.

| Criterion | Required invariant | How to check | Violation | Allowed correction | Validation |
|---|---|---|---|---|---|
| Readability | A frontend developer can identify file purpose, function purpose, inputs, outputs, and side effects without the original prompt. | Inspect names, function length, branching, comments, call sites. | Unnamed intent, large mixed-purpose function, magic strings, prompt-shaped code, comments explaining obvious lines while invariants are hidden. | Rename, split local logic, extract constants, add short invariant comments. | Build; targeted scenario if behavior path changed. |
| Maintainability | A local change does not require editing unrelated features. | Trace imports, globals, shared helpers, duplicated rendering, event listeners. | Hidden coupling, duplicated feature rules, broad rewrite for local issue, shared helper containing product-specific behavior. | Move rule to correct layer, remove duplicate, keep helper generic, narrow side effect. | Build; affected scenario. |
| Responsibility | Data, domain rules, UI behavior, shared UI helpers, and styles stay in their layers. | Compare file path to responsibility table and component spec. | UI invents data; DOM/React code owns filtering rules; styles encode behavior; generic helper owns product rule. | Move rule to `src/data`, `src/domain`, `src/features`, `src/ui`, or `src/styles` as appropriate. | Build; component behavior check. |
| Spec conformance | Code implements `01/02/03` without contradicting product behavior. | Compare visible structure, actions, states, counters, contracts. | Missing documented state, extra future behavior, wrong owner, undocumented visible behavior. | Fix code or update docs when code reflects real prototype behavior. | Build; affected component check; docs sync if behavior changed. |
| Security | Untrusted or variable data is inserted as data, not executable markup, code, URL, selector, or style. | Search `innerHTML`, string handlers, URL/image assignment, local paths, secrets. | Unsafe `innerHTML`, script-like string, unvalidated URL, leaked token/path, user text in selector/style. | Use text-safe DOM APIs, validate URL, remove secret/path/debug artifact. | Build; targeted render check. |
| Accessibility | Interactive and stateful UI remains operable and understandable beyond mouse-only and color-only usage. | Check accessible names, keyboard path, focus, visible state, table/card alternatives. | Button without name, focus removed, state only by color, drawer/modal strands user, count/status invisible to assistive flow. | Add native semantics/labels, preserve focus, add text/state indication. | Browser check where possible; build. |
| Performance | Frequent interactions do not do unnecessary heavy work or duplicate listeners. | Inspect input handlers, render loops, measure/mutate cycles, listener registration. | Full rebuild on every input when local update exists, repeated listeners after reopen, layout thrash, heavy dependency. | Debounce if needed, reuse derived data, attach listener once, localize update. | Build; repeat interaction check. |
| Generated code | Agent output follows local patterns and does not invent architecture. | Compare with neighboring files and existing helpers. | Invented API, unused file, future state, duplicate helper, broad rewrite, debug leftovers, code works only for one prompt case. | Reuse local pattern, remove invented parts, shrink change to request. | Build; regression scenario. |
| Dependencies/future work | New dependency, runtime stack, backend contract, or future feature appears only after explicit user instruction. | Inspect `package.json`, imports, new folders, generated TODOs. | React/DS in `vanilla-vite`, new package without need, backend stub, future feature. | Remove addition or stop for user approval. | `npm.cmd run build`; dependency diff. |

## Responsibility Table

Use this table as the S-Tracker layer contract.

| Layer | Allowed responsibility | Finding |
|---|---|---|
| `src/data` | Prototype data, dictionaries, task model, users, statuses. | Data duplicated or invented in UI code. |
| `src/domain` | Selection, filtering, grouping, pagination, columns, derived state. | Business rule hidden in DOM/React rendering code. |
| `src/features` | Behavior of large interface areas and product workflows. | Feature mutates unrelated feature internals without documented contract. |
| `src/ui` | Shared UI helpers and small reusable fragments. | Product-specific behavior hidden in a generic helper. |
| `src/styles` | Visual rules for the current prototype. | Behavior encoded only through CSS without matching JS/product state. |
| `index.html` | Static shell and stable mount structure. | Runtime behavior implemented inline without explicit reason. |
| `dist` | Build output. | Manual source edits made in `dist`. |

## Component Conformance

For a documented component, compare code against `01/02/03`.

| Spec file | Verify in code |
|---|---|
| `01-structure.md` | Visible zones, boundaries, entry points, layer, neighboring areas, visual states. |
| `02-behavior.md` | User actions, initial conditions, visible reactions, close/apply/reset/save/delete paths. |
| `03-data-states-rules.md` | State owners, counters, visibility rules, filtering, selection, pagination, columns, cross-component contracts. |

If implementation exposes real visible behavior not documented in `01/02/03`, report a documentation sync issue. Do not silently accept the gap.

## Vanilla/Vite Adapter

Use in `vanilla-vite` mode.

Check:

- ES modules use explicit imports/exports and run through Vite or another server, not fragile `file://` assumptions;
- DOM creation separates data derivation from element creation when practical;
- text values use text-safe APIs unless markup is static and controlled;
- document-level listeners are registered once or guarded against duplication;
- global `window` state has an owner and is not a hidden cross-feature bus without reason;
- card view and table view paths are explicit where behavior differs;
- CSS classes represent visual state that JS or data state can explain;
- `dist` is not edited manually.

Flag React, JSX, ReactDOM, Tend UI, Material UI, `@10d`, or similar DS runtime imports as `P1` unless the user explicitly authorized migration.

## React + Design-System Adapter

Use only in `react-design-system` mode.

Check React code:

- component name, props, local state, derived data, effects, and rendered output are clear from the file;
- product state owner is explicit: parent component, store/context, URL, server result, or local component state;
- state is not duplicated between parent and child without synchronization rule;
- derived values are computed from source state instead of stored separately unless there is a concrete reason;
- effects have a product reason, correct dependencies, and cleanup when they subscribe, listen, or start async work;
- lists have stable keys from task/domain/attribute identity, not array index when order can change;
- callbacks and memoization solve a measured or clear re-render problem, not decorative optimization;
- component props describe product input and output; child components do not mutate parent data directly.

Check design-system usage:

- use the corporate component named in the component spec or DS-binding map when available;
- do not recreate built-in `Select`, `MultiSelect`, `Input`, `Checkbox`, `Button`, `Drawer`, `Modal`, `Table`, `Toast`, tooltip, overlay, or focus mechanics unless the DS lacks that capability and the user approves custom work;
- keep S-Tracker product conditions in app code: when control is visible, disabled, selected, applied, saved, reset, or counted;
- treat standard hover, focus, pressed, keyboard navigation, focus trap, scroll lock, dropdown mechanics, and default overlay behavior as DS responsibility unless S-Tracker has a product-specific exception;
- do not override DS styling to imitate the old prototype if the DS component already defines the visual language.

Check CSS/CSS-in-JS:

- styling should express layout and product-specific visual distinctions, not business logic;
- design tokens and DS theme primitives should be used when the migrated stack provides them;
- generated inline styles must not contain dynamic behavior that belongs in state or props.

## Accessibility Audit

Use product-level accessibility checks in both runtime modes.

Require:

- interactive elements have accessible names;
- keyboard path exists for custom controls not covered by native/DS behavior;
- focus is visible or inherited from DS; custom code must not remove it without replacement;
- status, error, empty, selected, disabled, and count changes are visible in text or controls, not only color;
- drawer/modal/floating panel interactions do not strand the user;
- table and card alternatives preserve task identity and primary actions.

Use WCAG 2.2 principles as the external baseline when uncertain.

## Performance Audit

Use user-visible performance checks.

Flag:

- expensive filtering, sorting, or rendering inside uncontrolled input loops;
- repeated full DOM or React tree rebuilds during frequent interactions when local update is enough;
- duplicated event listeners or subscriptions after repeated open/close cycles;
- measure/mutate layout cycles that can cause visible jank;
- added dependency or asset weight that does not support the request;
- React re-renders caused by unstable props, keys, or state ownership in frequently changing lists.

Use Core Web Vitals concepts as guidance for responsiveness and layout stability, not as a requirement to run full production measurement for every prototype edit.

## Security Audit

Use frontend security checks in both runtime modes.

Flag:

- untrusted or variable data inserted through `innerHTML` or equivalent raw HTML APIs;
- URL, image, link, or style values inserted without validation;
- event handlers built from strings;
- user-provided text used as selector, HTML, script, style, or unsafe URL;
- secrets, tokens, local absolute paths, temporary file paths, or debug traces committed to code;
- dependency additions with unclear source or purpose.

Use OWASP XSS prevention and client-side security guidance when uncertain.

## Validation

Run the smallest useful validation.

For runtime code changes in current S-Tracker, run:

```powershell
npm.cmd run build
```

Use targeted searches as relevant:

```powershell
rg -n "React|ReactDOM|JSX|@mui|Material|Tend UI|TNUI|@10d" index.html package.json src docs
rg -n "TODO|FIXME|console\\.log|debugger|innerHTML" src index.html
```

In `react-design-system` mode, React search is not a failure by itself. Instead search for unauthorized legacy/runtime mixing, unsafe raw HTML, invented DS names, and new dependencies.

If lint/test scripts exist in `package.json`, consider them part of validation for code changes. Do not add ESLint, test frameworks, or new scripts unless the user asks.

## Output Contract

For read-only audit, lead with findings:

| Field | Required content |
|---|---|
| Severity | `P0`, `P1`, `P2`, or `P3`. |
| Location | File and line. |
| Criterion | Which audit criterion failed. |
| Evidence | Exact code behavior or snippet summary. |
| Risk | What can break or become hard to maintain. |
| Recommendation | Concrete correction. |

For edit tasks, report:

- files changed;
- runtime mode used;
- behavior preserved or changed;
- component docs updated or intentionally left unchanged;
- validation run and result;
- remaining risks or manual checks.

Do not claim production readiness unless build and relevant behavior checks passed.

## External Baselines

Use these as background baselines, not as files to load every time:

- MDN JavaScript modules for ES module structure and local-server requirements;
- React official docs for components, props, state, hooks, and effects in `react-design-system` mode;
- WCAG 2.2 for accessibility principles;
- OWASP XSS prevention and client-side security guidance for frontend security;
- Core Web Vitals for user-visible performance concepts;
- ESLint rule categories for possible JavaScript problems;
- Testing Library guiding principle: confidence grows when checks resemble user behavior.
