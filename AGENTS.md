# AGENTS.md

## Назначение
S-Tracker - прототип системы управления задачами по бизнес-доменам.
Цель работы: сохранять рабочий прототип и постепенно улучшать структуру проекта.

## Главный принцип
Сначала работоспособность. Потом рефакторинг.
Любое изменение должно сохранять текущие пользовательские сценарии.

## Нельзя ломать

- открытие и сборку проекта;
- список задач и режим "Все задачи";
- переключение бизнес-доменов;
- статусы над таблицей;
- поиск и фильтры;
- настройки колонок;
- библиотеку атрибутов;
- пресеты колонок;
- связь данных, фильтров, колонок и таблицы.
- вкладку `Поиск` и документный поиск внутри основной структуры S-Tracker.

## Источник истины
Данные: `src/data`.
Главная модель задач, доменов, очередей, атрибутов и значений: `src/data/task-model.js`.
Правила выборки, фильтрации, колонок и сборки строк таблицы: `src/domain`.
Поведение интерфейса: `src/features` и `src/ui`.
Внешний вид: `src/styles`.
UI не должен сам придумывать данные, атрибуты или доменную структуру.

Переиспользуемые UI-компоненты находятся в `src/ui/components`, а их реестр - в `src/ui/components/registry.js`.
Новые интерфейсы разделов и локальных стендов используют существующий компонент из реестра и не создают собственную кнопку, поле, селект, чекбокс, переключатель, пагинацию, drawer, modal или toast при наличии подходящей общей реализации.
Storybook в `.storybook/` показывает реальные компоненты из `src/ui/components`, а не копии их разметки.

Раздел `Поиск` использует разметку внутри `#js-esm-search-section`, runtime из `src/features/search` и стили из `src/styles/features/search-workspace.css`.
Документный поиск не хранит состояние внутри task runtime S-Tracker. Состояние поиска документов, фильтров документов, таблицы документов и слоев поиска остается внутри модулей `src/features/search/runtime`.
Не подключать React, Tend UI, Material UI или новые зависимости без отдельной прямой команды пользователя.

## Документация
Общее понимание проекта: `PROJECT-OVERVIEW.md`.
Пользовательские пути: `docs/user-flows`.
Компоненты интерфейса и главный чертеж UI: `docs/components`.
Документация одна для команды и AI-агента: это конкретная спецификация интерфейса, а не абстрактное описание.
Стандарт оформления документации: `docs/documentation-standards.md`.
Вся документация в `docs/` должна соответствовать `docs/documentation-standards.md`.

Экспортируемый контекст для фронтенд-разработчика: только комплект конкретного компонента в `docs/components/<component>/`.
Остальные документы в `docs/` являются инфраструктурой создания, проверки и сопровождения компонентных спецификаций для главного агента и субагента.
Если `01-structure.md` компонента содержит готовый визуальный эталон, локальное изображение внутри папки компонента входит в экспортируемый контекст для задач на компоновку. Зарезервированный путь без файла не считается готовым эталоном.
Готовый визуальный эталон должен фиксировать сам компонент или конкретное состояние компонента и минимальный соседний контекст; полноэкранный скриншот допускается только как сырой материал для последующей обрезки.
Если сквозной сценарий требует несколько визуальных состояний, изображения хранятся в папках компонентов-владельцев, а flow только связывает эти эталоны с шагами сценария.
Если правило из `docs/user-flows/`, `docs/entities/`, `docs/glossary.md`, `docs/component-code-map.md` или служебного документа нужно для генерации компонента, это правило должно быть внесено в `01/02/03` соответствующего компонента.

Если изменение влияет на видимое поведение интерфейса, проверить связанные документы.

Видимое поведение считается измененным, если меняется:

- действие пользователя;
- реакция интерфейса на действие;
- открытие, закрытие, применение, сброс, удаление или сохранение;
- состояние элемента: active, disabled, selected, empty, error;
- результат в соседнем компоненте;
- порядок или доступность пользовательского шага.

Если изменение затрагивает сквозной сценарий через несколько компонентов, обновить соответствующий файл в `docs/user-flows/` и проверить, нужно ли перенести измененное правило в `01/02/03` затронутых компонентов.
Соответствующий flow - это файл, который описывает измененный пользовательский путь.
Если такого файла нет, создать его только тогда, когда сценарий выходит за рамки одного компонента.

Если изменение затрагивает компонент, обновить его комплект в `docs/components/<component>/`:

- `01-structure.md`, если изменилась структура, состав зон, элементы, расположение или границы;
- `02-behavior.md`, если изменились действия пользователя или реакции интерфейса;
- `03-data-states-rules.md`, если изменились состояния, данные, правила видимости, счетчики или контракты с другими компонентами.

Если изменение является внутренним рефакторингом без изменения видимого интерфейса, компонентную спецификацию и flow не менять.
Если при этом логика переехала в другие файлы, обновить `docs/component-code-map.md`.
`docs/component-code-map.md` не является экспортируемым контекстом фронтенд-разработчика.

## Особенности проекта
Текущие бизнес-домены - набор для одной роли, а не полный список системы.
Разные роли могут видеть разное количество бизнес-доменов.
Документный поиск во вкладке `Поиск` перенесен в `src/features/search`.
`dist` - результат сборки. Основные правки делать в `index.html` и `src`.

## Правило удаления
Удалять можно только то, что точно не участвует в работе прототипа.
Перед удалением проверить `index.html`, `src/main.js`, импорты, сборку и влияние на интерфейс.
Если есть сомнение - не удалять.
