# S-Tracker: обзор проекта

## 1. Назначение

S-Tracker — рабочий прототип интерфейса управления задачами по бизнес-доменам.

Прототип показывает, как пользователь:

- выбирает область задач;
- переключает этап согласования;
- ищет задачу;
- применяет фильтры;
- смотрит задачи в карточном или табличном виде;
- настраивает колонки таблицы;
- использует библиотеку атрибутов и пресеты колонок;
- выбирает задачи и выполняет массовые действия;
- переходит между страницами отобранного набора задач.
- переключается в раздел `Поиск` и использует документный поиск внутри S-Tracker.

Проект не является полной копией промышленной системы и не содержит полный набор ролей, бизнес-доменов, backend-контрактов и серверных интеграций.

Текущая задача проекта — сохранять стабильный vanilla/Vite-прототип и поддерживать документацию, которая может использоваться как точный контекст для будущей генерации интерфейсов.

## 2. Роль этого файла

`PROJECT-OVERVIEW.md` дает общее понимание S-Tracker перед работой с кодом или документацией.

| Когда читать | Зачем |
|---|---|
| Первичный вход в проект | Понять назначение прототипа и основные области интерфейса. |
| Неясен продуктовый термин | Сверить смысл задачи, бизнес-домена, очереди, статуса, атрибута или колонки. |
| Нужно понять общий поток данных в интерфейсе | Увидеть, какие пользовательские условия формируют итоговый список задач. |

`PROJECT-OVERVIEW.md` не является:

- экспортируемым контекстом фронтенд-разработчика для генерации интерфейса;
- спецификацией конкретного компонента;
- стандартом написания документации;
- картой связи документации с файлами реализации;
- описанием backend-архитектуры.

Для генерации интерфейса фронтенд-разработчику передается комплект конкретного компонента из `docs/components/<component>/`.

## 3. Главный объект

Главный объект раздела `Задачи` — задача.

Раздел `Поиск` использует отдельную сущность документа. Документный поиск встроен в S-Tracker и не меняет модель задач.

| Данные задачи | Где видны в интерфейсе |
|---|---|
| Номер | Карточка задачи, строка таблицы, поиск, фильтрация. |
| Наименование | Карточка задачи, строка таблицы, поиск, фильтрация. |
| Бизнес-домен | Левая навигация, режим `Все задачи`, таблица, фильтры, настройки колонок. |
| Этап согласования | Сегменты над списком задач и отбор задач по активному сегменту. |
| Статус задачи | Цветной тег в карточке или строке задачи. |
| Исполнитель, автор, наблюдатели | Карточка, таблица, фильтры, группировка, поиск. |
| Атрибуты задачи | Колонки таблицы, фильтры, группировка, библиотека атрибутов. |

Этап согласования и статус задачи — разные значения.

| Термин | Что означает | Где отображается |
|---|---|---|
| Этап согласования / очередь | Положение задачи относительно рабочего маршрута пользователя. | Сегмент-контрол над списком задач. |
| Статус задачи | Продуктовое состояние самой задачи. | Цветной тег внутри карточки или строки. |

## 4. Основной принцип отбора задач

Список задач показывает результат нескольких условий, примененных к общему набору задач.

| Условие | Где задается | Что меняет в списке задач |
|---|---|---|
| Область задач | Левая навигация | Ограничивает задачи режимом `Все задачи`, бизнес-доменом, значением группировки, пользовательской группой или закладкой. |
| Этап согласования | Сегменты над списком задач | Оставляет задачи активного этапа, если выбранная область поддерживает сегменты. |
| Поисковая строка | Панель инструментов | Оставляет задачи, которые проходят текстовый поиск. |
| Примененные фильтры | Панель фильтрации | Оставляет задачи, которые проходят все активные параметры фильтрации. |
| Сортировка или порядок текущего набора | Список задач | Определяет порядок задач до пагинации, если такая логика активна в текущем представлении. |
| Текущая страница | Пагинация | Показывает только часть отобранного набора задач. |

Настройки колонок не меняют состав задач. Они меняют только набор, порядок и видимость колонок в табличном отображении.

Массовые действия не задают отбор задач. Они работают с задачами, которые пользователь выбрал через чекбоксы в карточках, строках или заголовке таблицы.

## 5. Бизнес-домены

Бизнес-домен — рабочая область задач.

Текущий демонстрационный набор бизнес-доменов:

| Бизнес-домен | Назначение в прототипе |
|---|---|
| `Строительные договоры` | Задачи по согласованию и сопровождению договоров. |
| `Закупки ТМЦ` | Задачи по заявкам, поставкам и закупкам ТМЦ. |
| `Поручения СД` | Задачи по поручениям и замечаниям строительного директора. |

Этот набор относится к текущей роли пользователя в прототипе. В полной системе разные роли могут видеть другой состав бизнес-доменов и другую последовательность пунктов в левой навигации.

Режим `Все задачи` не является отдельным бизнес-доменом. Он объединяет задачи всех бизнес-доменов, доступных текущей роли пользователя.

## 6. Основные области интерфейса

Актуальные компонентные спецификации находятся в `docs/components/`.

| Область | Папка спецификации | Что описывает |
|---|---|---|
| Верхняя навигация приложения | `docs/components/app-header/` | Пункты верхней навигации, активный раздел и переключение рабочих областей `Задачи` / `Поиск`. |
| Рабочая область поиска | `docs/components/search-workspace/` | Область документного поиска под хедером S-Tracker и ее изоляцию от рабочей области задач. |
| Левая навигация | `docs/components/left-navigation/` | `Все задачи`, бизнес-домены, группировки, пользовательские группы, закладки и изменение ширины панели. |
| Панель инструментов | `docs/components/toolbar/` | Поиск, переключатель карточного/табличного вида, открытие фильтров, быстрый сброс фильтров и действия верхней строки. |
| Очереди / этапы согласования | `docs/components/queues/` | Сегменты этапов, активный сегмент, счетчики и правила красной индикации. |
| Список задач | `docs/components/tasks/` | Карточный вид, табличный вид, строки, карточки, закрепленные колонки, пустое состояние и выбранные задачи. |
| Фильтрация | `docs/components/filters/` | Правая панель фильтрации, параметры, черновик выбора, применение и сброс. |
| Настройки колонок | `docs/components/column-settings/` | Правая панель настройки колонок, общие атрибуты, черновик, применение и дочерние зоны. |
| Пресеты колонок | `docs/components/column-settings/presets/` | Базовое отображение, сохраненные пресеты, сохранение, выбор и удаление пресета. |
| Библиотека атрибутов | `docs/components/column-settings/attribute-library/` | Открытая и закрытая библиотека, поиск атрибута, добавление в общие атрибуты и возврат. |
| Массовые действия | `docs/components/bulk-actions/` | Выбор задач, плавающая панель массовых действий, счетчик выбранных задач и действия над выбранным набором. |
| Пагинация | `docs/components/pagination/` | Деление отобранного набора задач на страницы и переход между страницами. |

Компонентные папки являются главным источником точного описания интерфейса. Если этот обзор расходится с `docs/components/<component>/`, использовать компонентную спецификацию.

## 7. Атрибуты, колонки и библиотека атрибутов

Атрибут задачи — поле или признак задачи.

Колонка — видимое отображение атрибута в таблице.

| Ситуация | Видимый результат |
|---|---|
| Атрибут входит в базовый набор выбранного контекста | Колонка этого атрибута видна в таблице по умолчанию. |
| Атрибут скрыт по умолчанию | Атрибут находится в библиотеке атрибутов, если доступен для выбранного контекста. |
| Пользователь добавляет атрибут из библиотеки | Атрибут входит в черновик общих атрибутов и может стать колонкой после применения настроек. |
| Пользователь скрывает колонку | Колонка исчезает из таблицы после применения настроек; данные задачи не удаляются. |
| В режиме `Все задачи` атрибут неприменим к домену конкретной задачи | Ячейка этой задачи по такой колонке остается пустой. |

Пресет колонок сохраняет состав, порядок, видимость и библиотечное происхождение колонок для конкретного контекста.

Карточный вид задач не использует настройки колонок и пресеты колонок.

## 8. Данные и правила прототипа

Данные текущего прототипа находятся в `src/data`.

| Источник | Роль |
|---|---|
| `src/data/task-model.js` | Бизнес-домены, роль пользователя, доступы роли, очереди, атрибуты, значения атрибутов и сгенерированные задачи. |
| `src/data/users.js` | Пользователи, которые отображаются как авторы, исполнители или наблюдатели. |
| `src/data/statuses.js` | Соответствие видимых этапов согласования внутренним значениям очередей. |
| `src/data/task-statuses.js` | Статусы задачи, которые отображаются цветными тегами. |

Правила отбора и подготовки данных находятся в `src/domain`.

| Источник | Роль |
|---|---|
| `src/domain/task-selectors.js` | Выбор задач, бизнес-доменов, атрибутов и сборка строк таблицы. |
| `src/domain/filters.js` | Проверка задачи по примененным фильтрам. |
| `src/domain/columns.js` | Определение видимых колонок и правил настройки колонок. |
| `src/domain/pagination.js` | Расчет страниц для отобранного набора задач. |
| `src/domain/grouping.js` | Правила группировки задач. |
| `src/domain/state.js` | Начальное состояние интерфейса прототипа. |

UI не должен придумывать данные, атрибуты, домены или очереди самостоятельно. Видимый интерфейс использует данные и правила из этих слоев.

## 9. Поведение и внешний вид

Поведение интерфейса находится в `src/features` и `src/ui`.

| Источник | Роль |
|---|---|
| `src/features/tasks/` | Карточный и табличный список задач, сегменты, строки, карточки и итоговый видимый набор. |
| `src/features/sidebar/` | Левая навигация, выбор области задач, счетчики, группы и закладки. |
| `src/features/filters/` | Панель фильтрации и мультивыборы. |
| `src/features/columns/` | Панель настройки колонок, библиотека атрибутов и пресеты. |
| `src/features/task-selection/` | Выбор задач и плавающая панель массовых действий. |
| `src/features/pagination/` | Элементы пагинации. |
| `src/features/search/` | Переключение верхних разделов `Задачи` / `Поиск`, runtime документного поиска, таблица документов, фильтры документов, шаблоны, массовые действия, дроверы и настройки колонок документов. |
| `src/features/grouping/` | Действия группировки в таблице. |
| `src/ui/` | Общие UI-помощники, иконки, пустое состояние, toast-уведомления и корневая компонентная база в `src/ui/components/`. |

Внешний вид находится в `src/styles`.

`dist` — результат сборки. Основные правки выполняются в `index.html` и `src`, затем сборка пересоздает `dist`.

| `docs/component-code-map.md` | Связь компонентных спецификаций с текущими файлами реализации; не передается фронтенд-разработчику как контекст генерации. |

Если правило из инфраструктурной документации нужно для генерации интерфейса, это правило должно быть внесено в `01/02/03` соответствующего компонента до передачи контекста фронтенд-разработчику.

## 11. Текущее технологическое состояние

Текущий прототип работает как vanilla JavaScript-приложение на Vite.

Вкладка `Поиск` работает из основной структуры S-Tracker. Разметка находится внутри `#js-esm-search-section`, поведение находится в `src/features/search`, стили находятся в `src/styles/features/search-workspace.css`. Состояние документного поиска отделено от состояния рабочей области задач.

На текущем этапе в S-Tracker не выполняется миграция на React и не подключается корпоративная дизайн-система как runtime-слой.

Текущие vanilla-компоненты S-Tracker зарегистрированы в `src/ui/components/registry.js` и показываются в корневом Storybook. Разделы `Задачи`, `Поиск` и будущий runtime локальных стендов переиспользуют эти реализации; продуктовые данные и сценарии остаются в соответствующих feature-модулях.

Будущая интеграция с корпоративной библиотекой компонентов должна выполняться только после отдельного решения пользователя. До такого решения проект сохраняет текущую vanilla/Vite-структуру.

## 12. Что важно сохранять

При изменении проекта нельзя ломать:

- открытие и сборку прототипа;
- выбор `Все задачи`;
- выбор бизнес-доменов;
- сегменты этапов согласования над списком задач;
- поиск;
- фильтры;
- карточный и табличный вид списка задач;
- настройки колонок;
- библиотеку атрибутов;
- пресеты колонок;
- массовые действия;
- пагинацию;
- связь выбранной области, очереди, поиска, фильтров, колонок и списка задач.

Если изменение меняет видимое поведение интерфейса, нужно проверить соответствующую компонентную спецификацию в `docs/components/<component>/` и связанный user-flow, если сценарий проходит через несколько компонентов.
