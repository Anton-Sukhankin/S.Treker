# Компоненты интерфейса

Комплект `task-card-drawer/` описывает правую карточку задачи и вложенную Lego-форму этапов. Точкой входа служит наименование позиции из комплекта `tasks/`.

Эта папка хранит спецификации компонентов интерфейса.

Старые короткие документы формата `interface.md` + `mechanics/` удалены. Они не являются источником истины и не должны использоваться как контекст для AI-агента.

Папка конкретного компонента является экспортируемым контекстом для фронтенд-разработчика. В этот контекст входят только документы самого компонента, локальные визуальные эталоны, если они указаны в `01-structure.md`, и дочерние зоны.

## Текущая структура

Сейчас в целевом формате описаны:

- `app-header/` - верхняя навигация S-Tracker и переключение рабочих областей `Задачи` / `Поиск`;
- `search-workspace/` - рабочая область поиска документов, подключенная под хедером S-Tracker;
- `documents-list/` - таблица выдачи документов в разделе `Поиск`;
- `document-bulk-actions/` - плавающая панель массовых действий документов в разделе `Поиск`;
- `document-package-selector/` - дерево выбора пакетов в модальном окне `Добавить в пакет`;
- `document-relations-drawer/` - правый дровер связей документа в разделе `Поиск`;
- `search-filters/` - левая панель условий поиска документов в разделе `Поиск`;
- `search-filter-templates/` - сохранение, применение и удаление шаблонов поиска документов;
- `document-column-settings/` - настройки колонок таблицы документов в разделе `Поиск`;
- `filters/` - фильтрация задач;
- `toolbar/` - панель инструментов списка задач;
- `left-navigation/` - левая навигация с `Все задачи`, бизнес-доменами, группировками, пользовательскими группами и закладками;
- `queues/` - этапы согласования над списком задач;
- `tasks/` - карточный и табличный список задач;
- `column-settings/` - настройки колонок таблицы, включая список колонок, пресеты и библиотеку атрибутов.
- `bulk-actions/` - выбор задач, плавающая панель и массовые действия над выбранными задачами.
- `pagination/` - переключение страниц отобранного набора задач до пагинации.

## Верхняя навигация приложения

Верхняя навигация описана в трех файлах:

- `app-header/01-structure.md` - состав верхнего хедера, навигационные пункты и граница с рабочими областями;
- `app-header/02-behavior.md` - переключение `Задачи` / `Поиск`, закрытие task-слоев при переходе в поиск;
- `app-header/03-data-states-rules.md` - активный раздел, видимость рабочих областей и ограничения ответственности хедера.

## Рабочая область поиска

Рабочая область поиска описана в трех файлах:

- `search-workspace/01-structure.md` - расположение под хедером, видимость вместо task workspace, пространственный контракт и граница зон документного поиска;
- `search-workspace/02-behavior.md` - вход в поиск, внутренний поиск документов и возврат к задачам;
- `search-workspace/03-data-states-rules.md` - видимость области, изоляция состояний документного поиска и контракт с верхней навигацией.

Детальные зоны поиска документов описаны отдельными комплектами: `search-filters`, `documents-list`, `document-relations-drawer`, `document-bulk-actions`, `document-package-selector`, `search-filter-templates`, `document-column-settings`.

## Список документов

Список документов описан в трех файлах:

- `documents-list/01-structure.md` - расположение таблицы документов в рабочей области поиска, граница компонента, пространственный контракт, строки, колонки, индикаторы и внешние связи;
- `documents-list/02-behavior.md` - основной путь просмотра выдачи, изменение условий поиска, выбор строк, выбор всех видимых строк и меню строки;
- `documents-list/03-data-states-rules.md` - владельцы состояния выдачи, выбранных документов, колонок, пагинации, счетчиков, доступности и контрактов с соседними зонами поиска.

## Массовые действия документов

- `document-bulk-actions/02-behavior.md` - выбор документов, показ панели, связи документа, добавление в пакет, пометка на удаление, снятие пометки, скачивание без подтвержденного результата;

## Выбор пакетов документов

## Экспортируемый контекст компонента

Не передавать всю папку `docs/components`.

Фронтенд-разработчику передается только папка нужного компонента:

1. `01-structure.md`;
2. `02-behavior.md`;
3. `03-data-states-rules.md`.

Если компонент имеет `README.md`, этот файл передается вместе с комплектом только тогда, когда он описывает карту родительского комплекса или дочерние зоны.

Если `01-structure.md` содержит готовые локальные визуальные эталоны, эти изображения передаются вместе с Markdown-файлами для задач на компоновку. Эталон должен быть обрезан до компонента или его состояния и минимального соседнего контекста. Полноэкранный снимок не считается готовым визуальным эталоном.

Если задача включает дочернюю зону компонента, передается комплект этой дочерней зоны внутри папки компонента.

Если задача относится к сквозному пользовательскому пути, flow-файл может ссылаться на визуальные эталоны компонентов. Каждый такой эталон хранится в папке компонента-владельца состояния, а не в `user-flows/`.

`../user-flows/`, `../entities/`, `../glossary.md`, служебные карты связи с кодом, `../templates/`, `../subagents/`, `../documentation-standards.md`, `../documentation-standards-audit.md` и `../project-structure.md` не входят в экспортируемый контекст фронтенд-разработчика.

Если информация из этих документов нужна для генерации компонента, она должна быть внесена в `01/02/03` этого компонента.

## Инфраструктурный контекст для агента и субагента

Полный маршрут выбора инфраструктурного контекста для главного агента и субагентов описан в [`../agent-context-routing.md`](../agent-context-routing.md).

Разделы `../documentation-standards.md` для компонентной задачи выбираются по таблице маршрутизации в `../agent-context-routing.md`, а не передаются субагенту всем файлом.

Если задача требует создания нового комплекта компонентной документации, использовать [`../templates/component-template.md`](../templates/component-template.md).

Если задача требует проверки, исправления или создания компонентной документации через субагента, использовать профиль [`../subagents/component-documentation-auditor.md`](../subagents/component-documentation-auditor.md) и skill `component-spec-audit`.

Если компонент использует общие интерфейсные данные прототипа, агент или субагент добавляет только нужный файл из [`../entities/`](../entities/) для подготовки спецификации и не передает всю папку сущностей без причины.

## Правило для следующих компонентов

Новые спецификации компонентов создавать только в новом формате.

Не возвращать структуру `interface.md` + `mechanics/`.

Не создавать много коротких файлов с абстрактными описаниями. Один компонент должен описываться небольшим числом конкретных файлов, которые можно передавать агенту как рабочий контекст.
