# Документация S-Tracker

Документация в `docs/` описывает текущий рабочий прототип как спецификацию интерфейса, поведения и правил состояния.

Главная цель: по документам должно быть понятно, что именно нужно собрать, изменить, проверить или сохранить в интерфейсе без чтения всего проекта.

## Главный источник

Основной источник по интерфейсу - `docs/components/`.

Документы компонентов являются конкретными чертежами: структура блока, состав элементов, действия пользователя, состояния, связи с соседними областями и правила, которые влияют на функциональность.

Только документы конкретного компонента из `docs/components/<component>/` являются экспортируемым контекстом для фронтенд-разработчика.

Правила подготовки документации находятся в `documentation-standards.md`.

Маршрут чтения для главного агента и субагентов находится в `agent-context-routing.md`.

## Структура

- `components/` - спецификации интерфейсных компонентов.
- `component-code-map.md` - связь спецификаций с файлами реализации.
- `component-library.md` - источник, реестр и правила использования общей компонентной базы и Storybook.
- `documentation-standards.md` - обязательный стандарт для всех документов в `docs/`.
- `documentation-standards-audit.md` - последний чекпоинт соответствия документации стандарту.
- `agent-context-routing.md` - правила выбора ограниченного пакета контекста для агента и субагентов, включая выбор применимых разделов `documentation-standards.md` по типу задачи.
- `entities/` - минимальный словарь общих интерфейсных данных прототипа.
- `glossary.md` - словарь терминов проекта.
- `project-structure.md` - общая структура проекта.
- `subagents/` - проектные профили временных субагентов для повторяемых задач с ограниченным контекстом.
- `templates/` - шаблоны создания и аудита документации.
- `user-flows/` - сквозные пользовательские пути, если сценарий выходит за рамки одного компонента.

## Действующие спецификации компонентов

Актуальная карта всех действующих компонентных комплектов находится в `components/README.md`.

`column-settings` является родительским компонентным комплексом. Внутри него отдельно описаны:

- `components/column-settings/presets/` - пресеты колонок;
- `components/column-settings/attribute-library/` - библиотека атрибутов.

Крупный компонент описывается комплектом:

- `01-structure.md`;
- `02-behavior.md`;
- `03-data-states-rules.md`.

Если `01-structure.md` содержит готовый визуальный эталон, локальное изображение внутри папки компонента передается вместе с Markdown-файлами для задач на компоновку. Готовый эталон показывает сам компонент или конкретное состояние компонента и минимальный соседний контекст; полноэкранный снимок используется только как сырой материал.

Если компонент имеет дочерние зоны, карта комплекта может быть вынесена в `README.md` внутри папки компонента.

## Экспортируемый контекст для фронтенд-разработчика

Фронтенд-разработчику передается только папка конкретного компонента из `docs/components/<component>/`.

В экспортируемый контекст входят:

1. `01-structure.md`;
2. `02-behavior.md`;
3. `03-data-states-rules.md`;
4. `README.md` компонента, если он описывает родительский комплекс;
5. локальные изображения визуального эталона внутри папки компонента, если они указаны в `01-structure.md` как готовые эталоны;
6. дочерние зоны внутри папки компонента, если они входят в задачу генерации.

Для задачи на сквозной пользовательский путь flow добавляется в рабочий пакет агента. Фронтенд-разработчику передаются комплекты участвующих компонентов и локальные визуальные эталоны из папок компонентов-владельцев ключевых состояний; правила flow, необходимые для генерации, должны быть внесены в `01/02/03` этих компонентов.

`user-flows/`, `entities/`, `glossary.md`, `component-code-map.md`, `templates/`, `subagents/`, `documentation-standards.md`, `documentation-standards-audit.md`, `project-structure.md` и `PROJECT-OVERVIEW.md` не передаются фронтенд-разработчику как контекст генерации интерфейса.

Если правило из инфраструктурного документа нужно для генерации компонента, оно должно быть внесено в комплект соответствующего компонента в `docs/components/<component>/`.

## Инфраструктурный контекст агента и субагента

Главный агент и субагент используют служебные документы для создания, проверки, исправления и сопровождения компонентных спецификаций, а также для аудита frontend-кода.

Подробное правило выбора инфраструктурного контекста описано в `agent-context-routing.md`. В нем же указано, какие разделы `documentation-standards.md` нужны для структуры, поведения, состояний, пользовательских путей, реализации функциональности и проверки качества.

## Служебные документы и skills

| Документ | Роль |
|---|---|
| `documentation-standards.md` | Нормативный стандарт. Имеет приоритет над шаблонами, профилями субагентов и skill. |
| `templates/component-template.md` | Практический каркас для создания или аудита комплекта `01/02/03`. |
| `templates/user-flow-template.md` | Практический каркас для создания или аудита сквозного пользовательского пути в `user-flows/`. |
| `subagents/component-documentation-auditor.md` | Профиль временного субагента для проверки, исправления и создания компонентной документации. |
| `../skills/component-spec-audit/SKILL.md` | Рабочая процедура аудита компонентных спецификаций. |
| `../skills/frontend-code-audit/SKILL.md` | Рабочая процедура аудита frontend-кода S-Tracker на поддерживаемость, соответствие спецификациям, доступность, производительность и безопасность. |
| `documentation-standards-audit.md` | Чекпоинт последней проверки соответствия документации стандарту. Не является инструкцией. |

Эти документы не должны дублировать друг друга полностью. Стандарт задает правила, шаблон дает форму, профиль задает роль субагента, skills задают порядок повторяемой проверки, audit фиксирует результат проверки.
