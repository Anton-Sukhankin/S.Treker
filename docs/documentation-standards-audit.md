# Аудит соответствия Documentation Standards

Дата проверки: 2026-07-31.

## 1. Назначение

Файл фиксирует последний результат проверки документации на соответствие `docs/documentation-standards.md`.

Чекпоинт не задает правила написания документации. Нормативный источник остается в `docs/documentation-standards.md`; рабочие процедуры остаются в `skills/component-spec-audit/SKILL.md` и `docs/subagents/component-documentation-auditor.md`.

## 2. Роль документов

| Документ | Роль | Статус |
|---|---|---|
| `docs/documentation-standards.md` | Нормативные правила компонентных спецификаций | Основной источник правил. |
| `docs/templates/component-template.md` | Каркас нового комплекта `01/02/03` | Синхронизирован с ролями файлов, пространственным контрактом, визуальным эталоном и границей дизайн-системы. |
| `docs/subagents/component-documentation-auditor.md` | Профиль временного субагента для проверки и правки компонентной документации | Используется вместе со skill `component-spec-audit`; требует проверки границ, зон, состояний, контрактов и точности формулировок. |
| `skills/component-spec-audit/SKILL.md` | Рабочая процедура аудита спецификаций | Содержит проверки абстрактных формулировок, пространственного контракта, визуального эталона, границы дизайн-системы и роли `03`. |
| `docs/agent-context-routing.md` | Правила выбора ограниченного пакета контекста | Отделяет экспортируемый компонентный контекст от инфраструктурных документов агента и субагента. |
| `docs/entities/` | Компактный словарь общих интерфейсных данных прототипа | Используется только если правило сущности нужно перенести в комплект конкретного компонента. |
| `docs/templates/user-flow-template.md` | Каркас сквозного пользовательского пути | Синхронизирован с правилом визуальных состояний сценария: изображения хранятся у компонентов-владельцев, flow связывает их с шагами. |

## 4. Выполненные проверки

| Проверка | Итог |
|---|---|
| Комплектность `01/02/03` | Все действующие комплекты из `docs/components/README.md` имеют `01-structure.md`, `02-behavior.md`, `03-data-states-rules.md`. |
| Роль `01` | `01-structure.md` содержит границу, расположение, зоны, состав, пространственный контракт и визуальный эталон или зарезервированный путь. |
| Роль `02` | `02-behavior.md` содержит действия пользователя, исходные условия и видимые результаты без полной карты состояний. |
| Роль `03` | `03-data-states-rules.md` содержит владельцев состояния, правила, счетчики, контракты и ограничения ответственности без повтора структуры и сценариев. |
| Statement-level точность | Риск-формулировки переписаны в правила с элементом, условием, изменением и видимым итогом. |
| Границы компонентов | Правила соседних компонентов вынесены из чужих комплектов; в компоненте оставлен только собственный видимый результат и внешний контракт. |
| Граница дизайн-системы | Внутренние механики готовых компонентов библиотеки не описаны как продуктовые правила S-Tracker. |
| Технические ссылки | В компонентных спецификациях не используются пути к `src/`, `index.html`, DOM, CSS, скриптам, временным папкам и абсолютным локальным путям. |
| Визуальные эталоны | Готовые изображения не создавались; зарезервированные пути указаны локально в формате `assets/<component>-<state>.png` без markdown-ссылок на отсутствующие файлы. |
| Граница кадра визуального эталона | Стандарт, шаблон компонента, шаблон flow, маршрут контекста, профиль субагента и skill фиксируют правило: готовый эталон обрезан до компонента или его состояния; полноэкранный снимок остается сырым материалом. |
| Наборы визуальных состояний flow | Для сквозных сценариев зафиксировано правило: каждый эталон хранится в папке компонента-владельца состояния, а flow только связывает изображения с шагами сценария. |
| Сквозной переход `Задачи` / `Поиск` | `docs/user-flows/section-switching-workflow.md` связывает `app-header`, рабочую область поиска и рабочую область задач без описания внутренних сценариев документного поиска. |
| Пост-интеграционный аудит `docs` | Архив интеграции документного поиска удален; активный контекст документного поиска находится в `docs/components`; инфраструктурные документы не передаются фронтенд-разработчику как экспортируемый контекст. |
| Очистка `user-flows` и `entities` | Flow-файлы сокращены до сквозных межкомпонентных результатов; entity-файлы оставляют только интерфейсные данные с активной UI-ролью. |

## 5. Не входило в текущую задачу

| Область | Статус |
|---|---|
| Реальные изображения визуальных эталонов | Остаются отдельной итерацией по компонентам. |
| DS-binding и названия компонентов корпоративной библиотеки | Остаются отдельной итерацией после готовности правил привязки дизайн-системы. |
| Полная проверка каждого утверждения по коду прототипа | Требует отдельного code-trace аудита с чтением релевантных файлов реализации. |
| Реальные изменения кода по итогам аудита `docs` | Не выполнялись; аудит изменял только Markdown-документацию и удалил архивные материалы без активной роли. |

## 6. Остаточные вопросы

| Вопрос | Следующий шаг |
|---|---|
| Визуальные эталоны сложных компонентов | Создать локальные изображения в папках компонентов и проверить совпадение с пространственными контрактами. |
| DS-binding | Добавить названия компонентов корпоративной дизайн-системы в компонентные спецификации после утверждения правил привязки. |
| `docs/user-flows` | Обновлять только при изменении сквозного сценария между несколькими компонентами; локальные правила оставлять в `01/02/03` компонентов. |

Блокирующих несоответствий для работы главного агента и временных субагентов после текущего аудита не зафиксировано.
