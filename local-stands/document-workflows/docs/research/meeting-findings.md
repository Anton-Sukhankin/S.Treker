# Результаты разбора встречи по документным сценариям

## 1. Роль документа

Документ хранит исследовательский контекст, который нельзя смешивать с подтвержденной компонентной спецификацией: замечания к показанному интерфейсу, дефекты демонстрационного стенда, гипотезы участников и вопросы без решения.

Компонентные требования находятся только в соответствующих комплектах `docs/components/<component>/`. Если гипотеза получит решение, правило переносится в `01/02/03` компонента и удаляется из списка нерешенных вопросов.

## 5. Подтвержденные решения

| Решение | Основание | Влияние на спецификации |
|---|---|---|
| Тип документа задает полную схему атрибутов. | Пояснение в начале встречи. | `documents-workspace` показывает схему выбранного типа; `document-templates-workspace` выбирает подмножество этой схемы. |
| Lego-шаблон организует пользовательские атрибуты по шагам и может связывать значения полей. | Демонстрация создания приказа и обсуждение автоподстановки подписанта. | `lego-document-form` поддерживает шаги, обязательность, значения по умолчанию и зависимые значения. |
| Обязательные атрибуты типа документа должны входить в шаблон. | Демонстрация корзины атрибутов. | Обязательные карточки нельзя исключить из будущего черновика. |
| Одна Lego-форма используется самостоятельно и внутри задачи. | Обсуждение после сохранения документа. | Создается один общий компонент с двумя контекстами запуска. |
| Верхняя часть карточки задачи в первой задаче не перепроектируется. | Уточнение в конце встречи: верхняя часть «прибита гвоздями». | `task-card-drawer` фиксирует верхнюю часть внутри drawer; прорабатывается рабочая область. |
| Действия формы и действия задачи имеют разных владельцев. | Обсуждение двух наборов кнопок. | Завершение редактирования формы не завершает задачу; доступность `Завершить задачу` задается карточкой задачи. |
| Печатная форма существует не для каждого документа. | Демонстрация заявки без печатной формы. | После сводки шаг верификации показывается только при наличии печатной формы. |
| Полный редактор шаблона после корзины атрибутов — отдельная задача. | Прямое решение на 20-й минуте встречи. | Первая спецификация шаблонов заканчивается созданием черновика. |

## 6. Замечания и наблюдавшиеся дефекты

| Область | Наблюдение | Требуемое правило для будущего прототипа |
|---|---|---|
| Состояние шагов | После возврата назад завершенный шаг мог терять зеленое состояние. | Завершенность шага вычисляется из валидного сохраненного состояния и не сбрасывается навигацией. |
| Значения по умолчанию | Пользователю приходилось прокликивать поля, хотя значение уже показано по умолчанию. | Валидное значение по умолчанию участвует в проверке без дополнительного клика. |
| Завершение формы | Кнопка завершения редактирования становилась доступна до последнего шага. | Завершение доступно только после прохождения всех применимых обязательных шагов. |
| Печатная форма | Для заявки без печатной формы показывался лишний экран превью. | Ветка генерации и проверки пропускается полностью, если печатная форма неприменима. |
| Связь атрибутов и печати | Изменение значения не всегда отражалось в печатной форме. | Сводка и печатная форма используют одно подтвержденное состояние атрибутов. |
| Кнопки задачи и формы | Два набора действий воспринимались как дублирующие. | Подписи, расположение и доступность должны показывать различие владельцев; окончательная компоновка требует отдельного решения. |
| Каталог шаблонов | Копирование и обновление списка демонстрировали нестабильное состояние. | После действия строка и состояние каталога должны иметь один однозначный результат или понятную ошибку. |
| Ошибки | Демонстрационный интерфейс показывал либо техническую, либо недостаточно конкретную ошибку. | Сообщение указывает проблемный шаг или поле и действие для исправления. |

## 7. Гипотезы, не являющиеся требованиями

| Гипотеза | Потенциальная польза | Что нужно проверить |
|---|---|---|
| Автоматически переходить к следующему шагу после заполнения текущего. | Меньше действий в длинной форме. | Нужен ли пользователю явный момент подтверждения шага и не вызывает ли переход потерю контроля. |
| Разместить действия формы и задачи в общей верхней закрепленной зоне. | Уменьшение конфликта двух наборов кнопок. | Как визуально разделить владельцев и что происходит при прокрутке. |
| Показывать заполненные значения одной или тремя колонками. | Использование ширины экрана. | Читаемость длинных значений, адаптивность и единый режим по умолчанию. |
| Разрешить редактирование отдельных подстановок на экране верификации. | Быстрая коррекция печатной формы. | Двусторонняя синхронизация с атрибутами и список разрешенных для изменения полей. |
| Автоматически переносить существующие шаблоны. | Сокращение ручной работы при большом количестве шаблонов. | Источник, качество преобразования, объем ручной проверки и интерфейс обработки ошибок. |

До решения этих вопросов первая версия стенда не должна автоматически переходить между шагами, объединять панели действий, менять режим колонок по собственной логике или открывать редактирование печатной формы.

## 9. Критерий переноса гипотезы в спецификацию

Гипотеза становится требованием только после явного решения, содержащего:

1. компонент-владелец;
2. условие доступности;
3. действие пользователя или входное состояние;
4. точный видимый результат;
5. влияние на соседние компоненты;
6. нужное визуальное состояние, если текст не фиксирует компоновку однозначно.
